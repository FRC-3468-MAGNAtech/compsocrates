# CompSocrates

CompSocrates (CS): scouting app for two FIRST programs, FRC and FTC, on Next.js 16.3 / React 19 / TypeScript (strict). One site, one repo, one Firebase project (CS's), one account across both programs. FRC reads and writes the existing CompSocrates Firestore schema through an adapter (`data/cs/*`); FTC data lives under `programs/ftc/` (see Program model). Plan and status: `docs/MERGE_PLAN.md`.

## Program model
- `config/programs/{frc,ftc}.ts` implement `ProgramConfig` (brand copy, alliance size, season rule, Firestore prefix, greyed-out pages, `pagesConnected`). `useProgram()` / `useProgramConfig()` (`lib/program/context.tsx`) give the active program. A component asks the config; it never names a program.
- Routes: the signed-in app is `app/(app)/[program]/...` (`/frc/scout`, `/ftc/scout`). Source code keeps writing program-relative paths (`"/scout"`): import `Link` from `@/components/program/link` and `useRouter`/`usePathname` from `@/lib/program/navigation`, never `next/link` or `next/navigation` for those. `lib/program/paths.ts` is the one place a path gets its program. Old CS URLs and every unprefixed app URL redirect to `/frc/...` (`config/legacy-redirects.ts`, `APP_SEGMENTS`).
- Selector: home page cards, the sidebar, the dashboard header and a topbar chip (`components/program/program-switcher.tsx`; the grid icon and chip link to `/?choose=1`, which keeps a signed-in person on the home page). The last-used program is in localStorage and the `program` cookie (`lib/program/context.tsx`); `HomeRedirect` sends a signed-in person with history to that program's `/dashboard`, and with none shows the selector.
- Firestore: FRC collections stay at the root, untouched. FTC is `programs/ftc/<collection>` with the sister app's schema; build every program path through `lib/firebase/paths.ts` (`programPath`, `programCollection`, `programDoc`) with an explicit program. FTC rules are the `match /programs/ftc` block of `firestore.rules` (helpers prefixed `ftc_`); FTC code must not use collection-group reads of `scouts`/`players` (the root recursive rules evaluate against the FRC profile).
- `pagesConnected: false` (neither program uses it now) makes the shell show `ProgramGate` instead of the shared pages, because they read FRC collections through `data/cs`. Connecting a program means giving the shared pages a program-aware data layer first. Current status: `pagesConnected` is true for FRC and for FTC (`data/ftc/` is committed). FTC is connected one page at a time: `connection.paths` lists the connected paths (the list is in the config and `docs/REMAINING.md`; any other path shows `UnconnectedPage` inside the shell), and `connection.features` says which shell/page data features exist (assignments, sub-ins, practice, live, library, accuracy, changelog, applications, event lookup); a piece whose feature is off does not mount or read. Add a path only when its data layer is program-aware.
- Program-aware data: a hook asks `useProgramData()` (`lib/program/data.ts`, the one shared file that maps a program id to its port). A port (`lib/ftc/program-data.ts`, over `data/ftc/`) serves profile, team doc, scout entries, form entries and forms; `null` (the root program) means the hook keeps its own reads untouched. Non-hook writers take an optional trailing `program` (`saveEntry(..., program)`), like `lib/events/actions.ts`. `ProgramAuth` supplies the program's own profile as `useAuth().profile`.
- Team setup (memberships build 3): ONE screen for every program, `components/team-setup/team-setup-screen.tsx` (`TeamSetupView` draws it from props, `TeamSetupScreen` reads; the card is `components/auth/team-setup-card.tsx`, rendered only by the screen). Join a team first (code and name), then Apply for a team; the same words in both programs (`team-setup-parity.test.tsx` renders every state for every program, `team-setup-guard.test.ts` fails on a second one). An account with no team goes to `/<program>/apply-to-team` (`/finish-setup` redirects there). A person joins by code through `/api/team/membership/request-join` (switch ON) or the program's older route (`flows.legacyJoinPath`), never a client write; the screen reads pending requests ONCE (`/api/team/my-join-requests`) and cancels through `/api/team/cancel-request`. FTC approve and deny are still the client batches while the switch is OFF (`data/ftc/join-requests.ts`).
- Match library (`library` port in `ProgramData`): FTC has scheduled matches (teams, optional `scheduledTime`, no score) in `programs/ftc/libraryEvents` and `libraryMatches`; the hooks in `lib/match-library.ts` and `lib/library/store.ts` read through the port when there is one and keep their root reads otherwise. A read is two queries (`origin == "api"` shared docs, `teamId == mine` hand-made docs). Admin Panel tabs are one list per program (`ProgramConfig.admin`, resolved in `lib/admin/tabs.ts`).
- Practice (`practice` port in `ProgramData`, Batch 3): FTC solo practice reads and writes `programs/ftc/practiceSessions` (`data/ftc/practice.ts`, pure rules in `lib/ftc/practice.ts`): team-wide `teamId ==` reads, never by event, the sister app's native session doc, flags on the session (no `scoutingFlagStates`), a malformed doc is kept and flagged for an admin. `lib/practice-sessions.ts` and `lib/scout-entries.ts` take an optional trailing `program`; hooks read through the port when there is one. `live` and `lobby` are separate feature flags (both on for FTC since Batch 6; a program with a flag off has inert hooks and no entry points). A library match's official score is optional per alliance (`scoreKnown`); no score means no accuracy (null, never 0, `lib/practice-outcome.ts`). Difficulty cut-offs come from `ProgramConfig.gameDifficulty`. Practice is never closed by the submission switches, in either program (Session E). A practice session uses the program's built-in match form when the saved override has no alliance-role block (`formWithRoles`).
- Scout Accuracy, post-save accuracy and CSV import (Batch 4, D26): `accuracy` and `csvImport` are on for FTC. `lib/scout-stats/*` reads through the same hooks (each source reports its own error, `sourceErrors`), actions take a trailing `program`, and the engine takes `entriesOnlyCount`, `seasonOfEntry` and `includeUnassigned` (off for FRC, so its numbers are unchanged). Only an admin writes derived accuracy fields (`lib/analytics/recompute-policy.ts`, `recomputeAfterSave`); CSV import is `lib/analytics/csv-import.ts` through `scoutEntries.importBatch`.
- Several teams per account (`multiTeam`, FTC only): the team doc lists `accountTeams`, `lib/our-team.ts` holds the one being viewed as (`useOurTeam`, `useAccountTeamChoice`, `useIsOurTeam` for any of them), and `FieldTeamSwitcher` (`components/program/field-team-switcher.tsx`; it switches FIELD teams, robot teams inside one team, and has nothing to do with memberships) renders only when the program allows it and the person has two or more. The membership `TeamSwitcher` is `components/team/team-switcher.tsx`.
- Team Settings and Changelog (Batch 5a, D27): `team-settings` is one page; a `multiTeam` program shows `AccountTeamsSection` (pure rules in `lib/account-teams.ts`, writes through `ProgramData.team.saveAccountTeams`, one batch with its audit entry) and `ProgramConfig.teamSettings` gates the Ownership card (the season's active form is chosen in Admin Panel > Forms, not here). A member sees only their assigned teams in the switcher, an admin all (`lib/our-team.ts`). `/api/ftc/team/sync-field-teams` (program REQUIRED in the body; admin or owner of the named team only) does the name `lookup` and an admin-only `sync` repair. The per-team changelog store and its starter drafts were replaced in Session 7 (the Platform changelog bullet below).
- Platform changelog and Credits (Session 7, D30): ONE changelog and ONE Credits for the whole site, edited by the platform owner only. Data: `platformChangelog/{id}` and `platformCredits/main`, read and written ONLY by Admin SDK routes (`lib/server/platform-*.ts`; `/api/platform/changelog`, `/api/platform/credits`, public `/api/public/credits`), never from the browser, no rules. An entry has `programs` (tags are data: one program id or both), `items[]` with an optional per-item `programs`, `legacy`, `rev`; credits carry a `version`. A stale edit is a 409 `conflict`. The Changelog page shows the current program's items plus the both-tagged ones (`entriesForProgram`, `lib/platform-changelog/model.ts`), a Show all programs switch, legacy entries below; the unread dot is `hasUnread` (published, non-legacy, an item for this program, newer than `lastSeenChangelogAt` and the account's creation); mark-seen is unchanged. `CreditsView` is the one Credits component at the public `/credits` and in each program's shell (`credits` is NOT in `APP_SEGMENTS`). The owner edits both in Admin Panel > Changelog / Credits (`platform-changelog`, `platform-credits` tab ids: in `PLATFORM_TABS` and in every program's tab list). No team is needed anywhere in this. `docs/SESSION7_RESULTS.md`.
- Admin Forms, Sessions, Rescore, Backups (Batch 5b, D28): the four tabs are shared panels; the program supplies data only. `lib/forms/firestore-store.ts` (store, `setActiveForm`), `lib/templates/firestore-service.tsx`, `rescore-sessions.ts` / `recompute.ts` writers and `lib/admin/backup.ts` take the program last (default: unchanged); FTC reads and writes `programs/ftc/forms|formTemplates|practiceSessions|scoutEntries` (and `ProgramData.backup` for the export). Templates live INSIDE the Forms tab (no `templates` tab id in FTC: that id is the owner-only Template Review); `ProgramConfig.admin.templateSharing` (off for FTC) hides public templates and publishing; apply goes through `/api/ftc/templates` (program REQUIRED in the body). The active match form is chosen in Forms (`teams.activeForms.{season}`); a form without the BIOBUZZ role block is never used for scouting (`formWithRoles` in `activeFormFor`). Rescore writes only derived fields (`lib/admin/rescore-apply.ts`: chunks of 400, partial failure stops with a count) and skips what has no official score. Backups: export only (`lib/ftc/backup.ts` never writes joinCode, email or tokens).
- Live and lobby practice (Batch 6): ONE set of screens; `ProgramData.live` and `ProgramData.lobby` (`data/ftc/live.ts`, `data/ftc/lobby.ts`, pure rules in `lib/ftc/live.ts` / `lib/ftc/lobby.ts`) over `programs/ftc/liveMatches/{key}/scouts`, `lobbies` and `players`. NO collection-group queries: "who is live on my team" derives the match keys from the team's open live sessions (`teamId ==`, `kind == live`) and reads each match's `scouts` by path with `teamId ==`; "the lobby I am in" lists `lobbies teamId ==` and, for each non-closed one, queries `players` by path with `teamId ==` and `uid ==` (a `get` of a missing player doc is denied by the rules, so it must be a query). Writers (`upsertPresence`, `claimLobbyId`, `updateLobby`, ...) take a trailing `program`. Server: `resolvePendingLiveMatches(db, messaging, uid?, program)` and `resolveLobbyResults(db, lobbyId, program)` read a `LiveProgramStore` (`lib/live/program-store.ts`; `lib/server/live-program.ts` maps a program id to it, the other program's is `lib/ftc/live-store.ts`); `/api/live/check-scores` and `/api/lobby/resolve-results` and `/api/live/detect-event` take `program` in the body, REQUIRED (`programFromBody` in `lib/server/live-program.ts`: missing or unknown = 400, a program whose `live`/`lobby` feature is off = 400 `program_not_supported`; never a default or a cookie), and both user routes check the caller's team in THAT program's users, the cron route sweeps every program. Alliance size comes from `ProgramConfig.event.allianceSize` (2 vs 3). `docs/BATCH6_RESULTS.md`.
- FTC event data: `lib/ftc/` (FTC Events API) behind `lib/events/actions.ts`, which takes an optional trailing `program` (default FRC). Missing keys return a typed `missing_credentials` error; FRC is unaffected.
- Event page and radar (Batch 7): `/events/[eventKey]` is one page; the key shape is `ProgramConfig.event.keyShape` (`lib/events/event-key.ts`: FRC `2026lake`, FTC `2025-USCALAB`), and every event read goes through `lib/events/event-queries.ts` (always passes `program`, keys scoped). Robot Radar is one page over `ProgramConfig.radar` (a profile per game: the hand-built `rebuilt` one, or `axes` read from the game's `radar` config; alliance axes use recorded-only means). Elements a game has no data for are hidden. `docs/BATCH7_RESULTS.md`.
- Migration: `scripts/migrate-ce-to-ftc.ts` (dry run by default; never run by the build or tests) with pure rules in `lib/ftc/migration.ts`.

## Folder layout
- `app/` Next.js App Router. `app/(app)` is the signed-in shell (one layout, auth redirect, page guard); `app/(marketing)` is public (landing, login, signup, legal); `app/api` holds the server routes.
- `config/` is the only place that names a product, game, event, API or alias. See `config/README.md`.
  - `brand.ts`: product name, copy, storage prefix, file and export markers, theme color and the logo slots.
  - `event.ts`: season, alliance size, API base URLs, event-key aliases, FIRST code overrides, fallback event key, playoff numbering.
  - `event-names.ts`: static event names (a step of the event-name fallback chain, D14).
  - `games/`: one `GameDefinition` per game (`rebuilt`, `reefscape`, `charged-up`), plus `shared.ts` and `index.ts`.
  - `legacy-redirects.ts`: every old CS URL and its destination (turned into permanent redirects by `next.config.ts`).
  - `cs.ts`, `alliance.ts`: CS identity (owner uid list, default theme) and robots per alliance.
- `config/games/ftc/` holds the FTC program's games in their own registry (D21); `lib/ftc/games.ts` builds their plugins and forms. They are not in the lists above.
- `lib/games/` game plugins behind one registry (`score`, `flags`, `normalize`, verification, prediction, rescout diff). `point-table.ts` generates the plugin for a pure point-table game from its config entry; `rebuilt.ts` is the hand-written plugin for REBUILT's fuel formulas. `cs-oracle/` holds verbatim copies of CS's own functions for golden tests only.
- `lib/events/` is the event facade (types, names, status, actions) and picks the provider per program; `lib/frc/` holds the FRC providers (TBA, FIRST FRC API, Statbotics) and `lib/ftc/` the FTC one.
- `lib/server/env.ts` is the only reader of server environment variables (see Rules).
- `data/cs/` is the adapter: typed converters between CS's Firestore documents and the app's own types (`ScoutEntry`, `FormEntry`, `TeamDoc`, `UserDoc`), plus fixtures and tests.
- `lib/our-team.ts` is the single seam for "our team" (one team per account): `useOurTeam`, `useIsOurTeam`, `OurTeamProvider`. A later multi-team switcher plugs in there and nowhere else (D13).
- `lib/forms/` is the form engine; `game-form.ts` builds a match form from a game definition. `components/`, `lib/` follow kebab-case with tests beside modules.
- Logo: the only artwork is `app/favicon.ico`. Every other logo slot (`mark`, `markDark`, `apple`, `pwa192`, `pwa512`, `pwaMaskable512`, `og`) is a field in `config/brand.ts` that is `null` until official artwork is supplied (D17). Do not add placeholder logos.
- `docs/`: `CS-REFERENCE.md`, `ROUTES.md`, `REMAINING.md`, `ENVIRONMENT.md`, `DEPLOYMENT.md`, `MOBILE.md`, plus `cs-firestore.rules` (CS's production rules, reference only) and `SECURITY-NOTES.md` (sensitive; keep it local).

## Conventions
- Next.js 16.3 App Router. Before writing Next code, read `node_modules/next/dist/docs/` (see AGENTS.md).
- TypeScript strict, `@/*` alias, ESLint flat config with `eslint-config-next`. There is no Prettier.
- Tailwind 4. Use the design tokens (`var(--muted-foreground)` and similar). No hardcoded colors or magic spacing.
- Touch targets are 44px or larger on coarse pointers, form text is 16px, and dialogs are bottom sheets on phones.
- Pure logic stays separate from Firebase code, with a `*.test.ts` beside it.

## Commands
- `npm run dev`, `npm run build` (runs the theme contrast guard first), `npm run lint`, `npm test` (Vitest).
- `npm run test:rules` needs Java and the Firebase CLI; it runs the Firestore and Auth emulators (`firebase emulators:exec`).
- `npm run test:e2e` is Playwright (`npx playwright install chromium webkit` once).

## Testing
- `npm test` runs unit tests (pure converters, game scoring, forms, analytics, routes' pure logic).
- `npm run test:rules` boots the emulators (project `demo-compsocrates-rebuild` from `.firebaserc`, so it cannot reach a real project) and runs the rules tests, the API route tests and the adapter integration tests.
- Game scoring is golden-tested against `lib/games/cs-oracle/` (test-only: do not import it from app code). A scoring change needs a golden test against CS documents.
- Never run a script or test against the production Firebase project. If you need real-looking data, copy it to a staging project first.
- Do not round-trip source files through tools that re-encode text (a scripted edit once garbled em dashes). Use the Edit tool.

## Data model and scoping rules
- Scope a read to what the page needs and no narrower. Event pages are event-scoped. Scout accuracy, scout stats and practice
  history are team-wide and cross-event: never filter them by the selected event.
- A CS document can lack the field the app's query filters on. Old CS read practice sessions by `scoutId` or `scoutName`
  (`teamId` is `""` when the scout had no team). Practice sessions are read in `lib/practice-extras.ts` (team query plus the team's
  members by uid and name, fetched once and shared); `data/cs/practice.ts` maps them. Do not add a `teamId ==` to a practice read.
- Session ownership is `scoutId`, else the member whose name matches (case-insensitive). Stats skip live (`csLive`), other-game,
  excluded (`excludeFromAccuracy` field or a `scoutingFlagStates` `practiceSession:<id>` row) and accuracy-less sessions; a missing
  accuracy is never a 0.
- A read that fails must say so: use `reportFirestoreError` and `describeFirestoreError` and show the error, never an empty list.
- Practice sessions must never be hidden by event-name resolution or event validation.
- Why: `docs/FIREBASE_FINDINGS.md`.

## Sidebar config (Session F, D24)
- `lib/nav.ts` is the list of pages that exist (`NavItem.id` is the stable id the config uses; never rename one, never key by label). `NAV_PAGES` is the flat list. A team arranges them in the doc `teams/{id}/settings/sidebar` (FTC: `programs/ftc/teams/{id}/settings/sidebar`, built with `programPath`): `{ version: 1, rev, entries[] }`, entry = `{ id, kind: "page"|"group", parent: null | "@footer" | groupId, order, label?, icon?, hidden? }`. Groups have a label and an icon and no route; nesting is one level. No doc means the default layout: today's list with every form page (the ones with a `formType`) in a "Forms" group.
- `lib/sidebar/`: `layout.ts` (default, `parseSidebarConfig`, `normalizeEntries`: every code page exactly once, unknown ids ignored, new code pages appended to their default group or zone), `resolve.ts` (`resolveSidebar({ program, isAdmin, can, config, labelOf, pathname })`: the ONE reader of the nav, used by the desktop sidebar and the mobile drawer), `edit.ts` (pure customizer operations), `icons.ts` (the icon allowlist, lucide icons the app already uses), `store.tsx` (`SidebarConfigProvider`, `useSidebarConfig`, `saveSidebarConfig`). Do not read `mainNav`/`secondaryNav` to render navigation; call the resolver.
- Visibility is cosmetic, not security. The resolver applies page access (`can`), the admin-only Admin Panel and the program's greyed-out pages AFTER the config, so a config can rearrange or hide but never grant or block a route. Lockout guard: a config that hides the Admin Panel from an admin, or leaves no visible page, is ignored (default layout). The customizer also refuses to save such a layout.
- The sidebar paints the cached config (localStorage, per program and team, brand `storageKey`) or the default first and swaps in the live doc; a failed read keeps the cache and shows an error only in Admin Panel > Sidebar. Open groups are remembered per device and program. Saves run in a transaction that compares `rev` (a conflict shows a message, never overwrites); the rules also require `rev + 1`. The sidebar and the builder name every page by its own `label` (`pageLabel`), never a game-prefixed form name (owner decision, Session E: no "REEFSCAPE Lead Scout Form" in the sidebar); an admin rename wins.
- Admin Panel > Sidebar (`components/admin/sidebar-panel.tsx`) is a DRAG AND DROP builder (@dnd-kit), never up/down arrows: the sidebar is one flat list (main list, a divider row, bottom block; a group's pages under it); drag a row by its handle up/down to reorder and sideways to nest a page in the group above or take it out. `lib/sidebar/dnd.ts` is the pure drop maths (`flattenRows`, `projectDrop`), `moveEntry` in `edit.ts` applies it. Keyboard: handle, Space, arrows (Left/Right = level), Space; the edit dialog has a Location select. Also rename and icon, hide, groups, reset one or all, live preview, Save/Discard, and a Sync card (`pushSidebarLayout` / `pullSidebarLayout` in `store.tsx`: copy the layout to, or load it from, the same person's team in the other program; a separate account there, so it needs a profile and admin rights there). Per-role layouts are out of scope (they would be one more optional `roles` field per entry, filtered in the resolver). Browser test: `e2e/sidebar-builder.e2e.ts` on `/e2e/sidebar-builder`.

## Memberships (build 1, additive; `docs/MEMBERSHIP_PLAN.md`, `docs/MEMBERSHIP_BUILD1_RESULTS.md`)
- One account, many teams. A membership is `memberships/{teamId}_{uid}` (FTC: `programs/ftc/memberships/...`, always built with `programPath`): `uid`, `teamId`, the role fields (`role`, `roles`, `secondaryRoles`, `isAdmin`, `isOwner`, `fieldTeamIds`; raw values, null = absent), `name` snapshot (never an email), `status` active|past, `origin` pointer|verified, epoch-ms `joinedAt`/`leftAt`/`updatedAt`, `endedBy`. `ProgramConfig.membership` maps each field to the program's own user-document field and holds `defaultJoinRole`; `lib/memberships/model.ts` is the pure part, `lib/server/memberships.ts` the Admin SDK part. `config/platform.ts`: `MAX_ACTIVE_MEMBERSHIPS = 5` per account across both programs. Ids reject "_" and "/".
- THE POINTER RULE: `users/{uid}.teamId` (FTC: the program's user doc) stays the ACTIVE team and the source of truth for the active team's role; every existing rule and query still reads it. An inactive team's role lives on its membership. Everything built from a pointer has origin `pointer` and may never grant what the pointer does not; only server-verified flows (a later session: join, approval, create, transfer) make `verified` ones, and only a verified active admin may read the past roster.
- Writes are server-only (rules: no client write). `POST /api/team/switch { program, teamId }` (program REQUIRED in the body) runs `switchActiveTeam` in ONE Admin SDK transaction: saves the outgoing role fields into the outgoing membership (creating it, origin pointer, if missing) and restores the incoming ones onto the user doc (a null field is deleted, never defaulted; `isPlatformOwner` is never touched). Errors: 400 program/team, 403 not_a_member / membership_ended, 409 no_profile / membership_limit / invalid_pointer, 404 memberships_disabled, 503 quota_exceeded.
- KILL SWITCH: `appSettings/global.membershipsEnabled` (missing = OFF, read through a ~30 s cache, `getMembershipsEnabled`). OFF: the sign-in hook does nothing, the switch route answers 404, the backfill refuses `--apply`. The sign-in sync (`ensureMembershipsOnSignIn`) never fails sign-in and caches "already ensured" for ~10 minutes per instance.
- `useAccountState()` (`lib/account-state.ts`) reads the memberships once per session (`getDocs`), falls back to ONE implicit membership from the profile pointer on permission-denied or an empty read, and is refetched only after `refreshAccountState()`. Nothing consumes it yet. `scripts/backfill-memberships.ts` (`npm run backfill:memberships`) is write-only and never run by the build or tests.

### Memberships build 2 (join, leave, removal, roles, roster seam, switcher; `docs/MEMBERSHIP_BUILD2_RESULTS.md`)
- ONE implementation for both programs: `lib/memberships/flows.ts` (pure rules), `lib/server/membership-flows.ts` (transactions), `lib/server/verify-admins.ts`, `lib/server/membership-route.ts` (token, 20 s deadline = 504 `timeout`, 503 `server_not_configured`, quota code 8 = 503 `quota_exceeded`, gRPC admin client). The program supplies data only: `ProgramConfig.membership.flows` (owner fields, request layout and field names, new-user shape, legacy admin role, `adminFlagLocked`). No program-id comparison in shared code.
- Routes (all need `program` in the body; all 404 `memberships_disabled` while the kill switch is OFF): `/api/team/join-lookup` (only `{ exists, allowsRoleChoice, alreadyMember, atLimit }`), `/api/team/membership/request-join`, `/api/team/membership/decide` (approve/deny, both programs), `/api/team/leave`, `/api/team/member/remove`, `/api/team/member/access`, `/api/platform/verify-admins` (platform owner; list is read-only, verify needs the ticked uids and the typed team name). The old routes and client batches stay for the switch OFF. `membershipsEnabled` is also in `/api/public/config` (how the browser learns it; `lib/memberships/client.ts`).
- VERIFIED memberships are made only by server flows: join approval, rejoin (same document, `rejoinedAt`, original `joinedAt`), team creation and application approval (FRC server routes), ownership transfer, and the owner's "Verify admins". The role at approval is decided by the server: the requested role only when the team's `allowMemberRoleChoice` is exactly `true` and the role is a valid non-admin one (`team-coach` is excluded too), else `defaultJoinRole`. Role edits write the user document only when the team is the person's active team, the membership only otherwise; `isPlatformOwner` is never written.
- Leave/remove: membership becomes `past` (leftAt, endedBy, snapshots), the pointer moves to the most recently active OTHER membership else `teamId: ""` and the team fields reset (profile and preferences kept). Guards: 409 `last_admin`, 409 `owner_must_transfer`; the sole member may leave; a platform owner's `force` skips the guards. An EMPTY team id means no team everywhere (FTC rule `ftc_sameTeam`/`ftc_hasTeam`, `ProgramGate`, the request-join route, the lobby route).
- Roster seam: `lib/team-roster.ts` (browser) and `lib/server/team-roster.ts`. OFF: exactly today's `users where teamId ==` read, zero membership queries (tested by counting). ON: plus one cached `memberships` read per (program, team) per page load, no listener; denied = users only. `invalidateRoster()` after a membership change.
- Switcher: `TeamSwitchProvider` (`lib/memberships/switching.tsx`) holds the shell on "Switching…" until the profile snapshot shows the target team, then `key={teamId}` remounts the shell, clears the roster cache and refreshes the account state. No shared draft detection exists, so there is no "unsaved changes" prompt before a switch.

### Memberships build 3 (applications, one Join / Apply screen, no-team accounts, personal practice, share on join; `docs/MEMBERSHIP_BUILD3_RESULTS.md`)
- Applications are the ONLY way to a new team, in both programs. `POST /api/applications` takes a REQUIRED `program`, answers 403 `applications_closed` unless `appSettings/global.teamCreationEnabled` is true (the Admin Panel's "Accept team applications"), and uses `programPath` collections (`teamApplications`, `applicationPrivate`, `applicationBlocks`, `platformAuditLog`); blocks and the one-pending rule are per program, a taken team number is checked per program (`flows.newTeam`). `lib/server/application-decisions.ts` is the one approval (`application-teams.ts` holds each program's document shapes): the pointer is set only for an account with no active team here; ON adds a VERIFIED owner membership and the 5-team cap; OFF is as before. `POST /api/team/create` is 410. The Applications panel (`components/admin/applications-panel.tsx`) is shared, one-time reads plus Refresh.
- Join requests: several pending (one per team, max `MAX_PENDING_JOIN_REQUESTS` = 5, the same team again = 409). A program that keeps requests under each team (FTC) has a server-only pointer `<program>/joinRequestPointers/{uid}` (`lib/server/join-pointers.ts`; no client rule matches it): a lead only, the request document is the truth.
- No-team accounts, gated by `membershipsEnabled` (OFF = exactly as before): `lib/personal/routing.ts` (`resolveShellRoute`, `PERSONAL_PATHS`) is the one routing rule; the shell provides `PersonalModeContext`, the sidebar has a personal mode (`resolveSidebar({ personal })`), the dashboard is `PersonalDashboard`, Profile is read-only, a platform owner (the token claim, `usePlatformOwnerClaim`) can open the Admin Panel's platform tabs. Sign-up asks for no team.
- Personal practice: `lib/personal/practice-store.ts` over `<program>/personalPractice/{uid}/sessions|entries|state` (rules: self by path, no `teamId` key, bounded). The practice and entry writers consult `personalScopeUid()` (`lib/personal/scope.ts`, set by the shell) FIRST; the shared library is read once (`usePersonalSeasonMatches`, `ProgramData.library.fetchSharedMatches`). Never a listener, never a team collection.
- Share on join: `POST /api/team/share-practice` (`lib/server/practice-sharing.ts`) copies completed sessions and their entries into the team the person is on (batches of 400, 3,000 writes per call, deterministic ids, marker `state/share`); the prompt is `SharePracticePrompt`.
- Closing rules (written, deploy by hand AFTER the app): FTC `teams` create and the same-batch owner profile create are `false`. The FTC approve and deny batches and the join-request self-create stay open while the switch is OFF; the root rules are unchanged.

### Memberships build 4 (account deletion; `docs/MEMBERSHIP_BUILD4_RESULTS.md`)
- A SERVER job, one implementation for both programs: `lib/server/account-deletion/` (`job.ts` steps, `engine.ts` runs the registry, `ports.ts` the three doors: store, Auth, Blob; `wire.ts` is the only Admin SDK half). Steps: disable the Auth user and revoke tokens, 70 minute COOLDOWN, rewrite, end memberships, delete, avatars, final SWEEP (must find nothing: a late write sends the job back, up to 3 loops, then `stalled`), delete the Auth user, delete the job document. Job document `accountDeletions/{uid}` (server only, no rule, NO name or email; the random opaque id `deleted-<32 hex>` lives only there and goes with it, so no mapping from the person to the id survives).
- THE REGISTRY (`lib/deletion/registry.ts`, `PERSON_DATA_REGISTRY`) is the single place future code must update when it stores a person (uid, name, email, token, photo): shared entries there, the program's own in `data/cs/deletion-entries.ts` and `lib/ftc/deletion-entries.ts` (`ProgramConfig.deletion`). `lib/deletion/registry.test.ts` fails on a collection named in `firestore.rules` or through the path helpers that has no row, and on a person-looking key a writer stores that no row lists (heuristic, allowlist with reasons in the test). The pure rewrite is `lib/deletion/rewrite.ts` (idempotent).
- Rules: kept rows get the opaque id and the name "Deleted Account" (`lib/deletion/constants.ts`); a membership is COPIED to `{teamId}_{opaque}` as `past`/`deleted` (its id held the uid); a team is never deleted (an ownerless team keeps `ownerUid` rewritten); rows with only a name are rewritten only for a name known for the person and never where another member of the same teams has it (counted and reported); `applicationBlocks` keeps its HMAC id and loses `value`; share-on-join ids (`{id}-{8 hex of sha1(uid)}`) stay. Never a collection-group query: presence is found through the match keys and lobby ids of the person's own sessions (saved in the job), assignments and lobbies by a team scan.
- Kill switch `appSettings/global.accountDeletionEnabled` (missing = OFF; cached helper `getAccountDeletionSettings` in `lib/server/team-settings.ts`) and `accountDeletionRunBudget` (positive integer, missing = 3,000 writes, cap 10,000; reads 4,000 per run). OFF: the routes answer 404 `deletion_disabled`, the dialog and the Admin Panel tab are hidden. Routes: `POST /api/account/delete` (recent sign-in, typed DELETE; 409 `last_admin`, 403 `platform_owner`, 409 `deletion_in_progress`), `POST /api/platform/account-deletions` (list, start, resume by opaque id), `GET /api/cron/account-deletions` (CRON_SECRET; daily on Vercel Hobby, a stalled job waits for the owner's Resume). It works with `membershipsEnabled` OFF (the pointer is the only membership).
- Everywhere a person is looked up by uid, use `personName` (`lib/people/display-name.ts`): a roster name, "Deleted Account" for an opaque id, "Former member" otherwise, never a uid.

## Alliance roles (BIOBUZZ)
- Objectives the alliance scores (BIOBUZZ's Hive, Flower, Garden) are recorded by ONE scout per alliance, or they double count. `allianceRoles` in the game config (`config/games/ftc/biobuzz.ts`) names two roles and their fields: **Hive** records Tip Hive (auto and teleop), **Garden** records Garden and Flower. Only BIOBUZZ has the block; FRC and the other games are untouched.
- The role is a seeded choice, never FRC's slot rule (`isHumanPlayerSlot`): `lib/forms/alliance-role.ts` hashes event, match type, match number and alliance (practice: library match plus session id) and one bit picks which of the alliance's two teams (sorted) is Hive. Both scouts compute it with no stored state. No role (roster unknown, not exactly two teams) means every field is shown.
- Stored on the entry as `values.allianceRole` (`"hive"`/`"garden"`). The other role's fields are ABSENT, not 0; a present value counts as recorded, in old entries too. Fields carry `allianceRole` and a `notEquals` `visibleWhen`. `normalizeValues` leaves a missing role field absent; `applyAllianceRole` is the one place that strips/fills them.
- Readers must treat absent as "not asked": team stats divide by recorded entries and are labelled alliance stats (`allianceStat`, "(alliance)" on cards); match breakdown shows alliance objectives once (`allianceObjectives`); Zero Main Scoring and Statistical Outlier flags account for it; CSV exports absent as an empty cell and imports it back as absent; the admin editor shows both roles and drops the role when an admin fills the other role's field.
- The scout form shows "You are scouting: Hive/Garden" only (never a total; see Session C). Practice difficulty cut-offs (`thresholds.difficulty`) are unchanged.

## Read budget (the free plan allows 50,000 reads a day; `docs/READ_REDUCTION_RESULTS.md`)
- Browser reads go through ONE door, `lib/firebase/metered.ts` (re-exports `firebase/firestore`; wraps `getDocs`, `getDoc`, `onSnapshot`). Never import those three straight from `firebase/firestore` (`lib/firebase/metered.guard.test.ts` fails). The door also feeds the read meter and the one quota banner (`lib/quota.ts`: `resource-exhausted` never wipes data on screen and a failed profile read is never "no profile").
- Read meter: OFF unless `appSettings/global.readMeterEnabled` is true (missing = OFF; zero reads and writes while OFF). Browsers keep counts in memory and flush through `POST /api/read-meter` to `readMeter/{Pacific day}` (Admin SDK, `FieldValue.increment`, no rules); listed server routes count through `meterDb` (`lib/server/read-meter.ts`, no SDK patching). Platform-owner tab `read-usage`; admins get a device-only counter with `?readmeter=1`. It does not see rule-evaluation reads. Heavy admin tools confirm with a COUNT-query estimate first (`lib/read-meter/estimate.ts`, `ProgramConfig.readEstimate`).
- `appSettings/global` is read through ONE shared 30 s per-instance snapshot (`readAppSettings` in `lib/server/team-settings.ts`) for the public config, the memberships and deletion switches and the meter switch.
- The legacy fallbacks (`lib/scout-entries.ts` `loadLegacyRows`, `lib/practice-extras.ts`) remember the kept rows per device for 6 hours (`lib/legacy-cache.ts`); they are NOT narrowed by `teamId == ""`. A new reader of team entries must not add its own member `in` queries.
- Test tooling for reads: `test-stubs/hook-runtime.ts` (hooks without jsdom), `test-stubs/fake-firestore.ts` (billing counters), `lib/read-counts.test.ts` (documents per page on a synthetic dataset) and `lib/read-reduction.characterization.test.ts` (displayed outputs; must not change).
- Local development: `npm run dev:emu` (`docs/LOCAL_DEV.md`); `npm run dev` uses whatever `.env.local` holds.

## Rules for changes
- Do not change CS's schema or scoring logic without approval. Additive fields are listed in `docs/REMAINING.md`; add to that list when you write a new one.
- **Environment:** the FTC keys (`FTC_API_USERNAME`, `FTC_API_KEY`, optional `FTC_API_BASE_URL`) are group `ftc` (section D of `.env.example`); the migration script alone reads `CE_ADMIN_*` and `CS_ADMIN_*`. Server code reads environment variables only through `lib/server/env.ts` (add the getter and an `ENV_VARS` entry, and keep `.env.example` and `docs/ENVIRONMENT.md` in step; a test checks the first two). Browser-inlined `NEXT_PUBLIC_*` values need a literal `process.env.NAME` access and are the exception. Never reference `NEXT_PUBLIC_TBA_API_KEY` from client code: despite its name it is a server secret.
- **Programs:** FRC-only and FTC-only names, fields and API calls stay in their own scoped files (`config/programs/<id>.ts`, `lib/frc`, `lib/ftc`, `data/cs`, `data/ftc`). Shared code reads `ProgramConfig`. A user in one program never sees the other's data or names.
- **Brand:** every user-visible product string, browser-storage key, exported-file marker and logo path comes from `config/brand.ts`. Do not write the product name or a storage key literal elsewhere.
- **Games, events, aliases:** change `config/`, not components. A new game is one `config/games/` entry (plus a plugin only for cross-field scoring).
- **Our team:** read the account's team through `lib/our-team.ts`, never from the team doc ad hoc.
- Run no code against production Firebase. Do not commit secrets or `docs/SECURITY-NOTES.md` to a public repository.
- Small, logical commits with clear messages. Add a row to the ROUTES decision table when you make a new decision, and a line to REMAINING when you leave something undone.
- Build, lint and tests must pass with no errors or warnings before anything is called done.

## Branches
- The working branch is `release-prep`. Every session commits and pushes there, and never to `main` or `master`.
- A release is a pull request from `release-prep` into `main`, merged with "Create a merge commit".
- `dev`, `membership`, `preview`, `rebuild`, `CompSocrates-v2`, the backup branches and the old branches are archival and must not receive commits. `main` receives releases only.
- The membership kill switch (`appSettings/global.membershipsEnabled`) stays OFF until the additive membership rules are deployed by hand; deploy them before turning the switch on, and preferably before the release that carries the code. The membership backfill is never run without a Firestore export and healthy read quota.
