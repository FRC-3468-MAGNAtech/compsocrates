# Membership plan (Session 4, plan only: no code, rules, data or config changed)

Goal: one account, many teams across FRC and FTC, a role per team, leave and removal that keep history, limited access with no team, safe account deletion, applications for every new team, identical screens. Everything is ADDITIVE: live CS shares this Firestore project, so existing fields keep their meaning and live CS ignores unknown fields/collections. Known weak spots in the current rules are tracked in the local-only security notes and are deliberately not described here. Facts below come from code reads by file:line; "unverified" marks what I did not confirm.

**Terms.** *Team* = a team document an account is a member of (root `teams/{id}` for FRC, `programs/ftc/teams/{id}` for FTC). *Field team* = an FTC robot team inside one FTC team (`fieldTeams`, user `fieldTeamIds`, the `accountTeams` list behind today's `TeamSwitcher` and `lib/account-teams.ts`; unverified that every use is field-team only, check in build session 2). They are different. The existing switcher becomes `FieldTeamSwitcher`; the new one is `TeamSwitcher`. *Membership* = one account's record in one team. *Active team* = the one `users/{uid}.teamId` points at, per program.

## 2. Membership data model
**Recommended (smallest additive):** a flat collection `memberships/{teamId}_{uid}` (FRC) and `programs/ftc/memberships/{teamId}_{uid}` (FTC), built with `programCollection`. Fields: uid, teamId, program-native role (`role`, `roles`, `isAdmin`, `isOwner`, `fieldTeamIds` for FTC), `name` (snapshot), `status` `active|past`, `joinedAt`, `leftAt`, `endedBy` `self|admin|deleted`. Queryable both ways (`uid ==` for "my teams", `teamId ==` + status for rosters) with equality filters only, so no composite index and NO collection-group query (the CLAUDE.md warning). **All membership writes are server-only** (rules: client write false). `users/{uid}.teamId` (and FTC `programs/ftc/users/{uid}.teamId`) stays the ACTIVE pointer that every existing rule and query keeps using.
- **Switch:** `POST /api/team/switch {program, teamId}`: verify an active membership, in one transaction save the outgoing role fields from the user doc into the old membership, then write teamId, role fields (and FTC `fieldTeamIds`) of the incoming membership onto the user doc. The active team's role lives on the user doc (live CS edits it there); inactive teams' roles live on the membership. Live CS ignores the new collection.
- **Rosters read memberships**, not `users where teamId ==`, behind one new seam `lib/team-roster.ts`. During the parallel run it is a union: active memberships plus `users where teamId ==` not yet backfilled (live CS joins create no membership). Sign-in (`sync-roles`) runs `ensureMembership` (pointer without membership: create it). A backfill script (dry run default, never run by build/tests) covers the rest. Risk: someone removed in live CS stays active here until cutover (unverified how CS removes).
- **Alternatives rejected:** (1) array/map on the user doc: client-writable data cannot carry membership or roles; rosters need cross-user reads that rules block. (2) Pointer only, user doc rewritten on switch: inactive members disappear from rosters and attendance. (3) `teams/{id}/members` subcollection: path-natural for rosters but "my teams" needs a collection-group query.
- **Active team and devices:** one active team per program per account, kept in Firestore (localStorage only caches first paint). Limitation: two devices cannot sit in different teams, because rules key on the pointer. The switcher shows a "switching" state until the profile snapshot lands, with sidebar/page-access stores reset (`loaded=false`) so the old team's `can` never meets the new teamId. The switcher lives in the topbar next to the program chip, one per program, plus "Join another team" opening the setup screen.
- **Existing rule weaknesses:** the design adds none (membership docs are not client-writable; the new rules use membership, not the pointer) and does not fix the existing ones, because live CS still depends on current behavior. The rebuild's client stops writing the pointer and role fields itself (role edits move to a route). Later hardening is an owner decision, after backfill: make `sameTeam()` also require an active membership, and tighten root user writes (details in the local security notes). FTC is already locked.
- **Roles per team:** program-native, from the membership. Default role on join: Match Scout in BOTH programs (`ProgramConfig.defaultJoinRole`, the program's own role id; verify the FRC id in build session 2). A team setting `allowMemberRoleChoice` (additive field on the team doc, default off, a toggle in Team Settings for both programs; the FTC team rule's key allowlist needs the new key) lets joiners pick: the Join screen stays unchanged, and when the team allows it the pending-request card shows a role select the requester can change until approval, written to `requestedRole`. The server decides at approval: the requested role only if the toggle is on and the role is valid, else Match Scout. Applications create teams with the toggle off. Platform owner needs no membership; `sync-roles` stops attaching them to "the only team", and the Admin Panel must open with no team. Owners of several teams: ownership stays on each team doc (`ownerUid`/`verifiedOwnerId`); Team Settings shows the active team's; Account Settings gets a "My teams" list (program, role, owner badge, Leave).
- **Views:** all team-scoped reads (My Scouting, Scout Accuracy, Analytics, Assignments) stay scoped to the active team. No cross-team aggregation (FTC rules would deny it, and team A must not see team B).

## 3. No-team accounts
- Identity: the ROOT `users/{uid}` doc is the account for both programs (it exists from sign-up with `teamId ""`). A no-team FTC account has no `programs/ftc/users` doc, so `useAuth().profile` is null; add one `useAccountState()` seam (`loading|no-team|team`, active team, memberships) and stop keying routing on `profile?.teamId`.
- Sees: Practice Scouting, Profile, Achievements, Account Settings, Credits, Changelog, plus the Join/Apply screen and, for a platform owner, the Admin Panel. No team data. Landing page = a no-team dashboard (Join with a code, Apply for a team, Practice). Sign-up stops asking for a team.
- Routing: replace "no team => redirect" with an allowlist `PERSONAL_PATHS`; no team and not on the list redirects to the dashboard; `/apply-to-team` is reachable for everyone (the "team member on setup route goes to /dashboard" rule is removed). Sidebar: `resolveSidebar` gets `personal: true` and shows only `PERSONAL_PAGE_IDS`, which bypass the team `can`. Never an empty screen: the dashboard is always allowed.
- **Practice:** matches come from the shared official library that already exists (root `practiceMatches`; FTC `libraryMatches` with `origin == "api"`), never team hand-made docs. Sessions go to `personalPractice/{uid}/sessions/{id}` (FTC: `programs/ftc/personalPractice/...`), entries beside them, accuracy computed by `lib/practice-outcome.ts` against the official score (null, never 0). Rules: self only by path, and the document must NOT carry a `teamId` key, so the empty-teamId bug cannot recur. Needs (unverified): the FTC library rule may require a team for `origin == "api"` reads; the root `profiles` create rule requires a team (`teamId ""` must be allowed for self).
- On joining: personal sessions stay private. A one-time prompt offers "share my practice history with this team", which a server route copies as team sessions with the new teamId (opt in, never automatic). A team can never see personal sessions, achievements or no-team profile unless shared; after joining it sees the membership roster fields only.

## 4. Leave, removal, past members
- **Leave/remove** (`POST /api/team/leave`, `/api/team/member/remove`; one transaction): membership `status=past`, `leftAt`, `endedBy`, name and role snapshot refreshed. If it was the active team, the pointer moves to the most recent other active membership, else `teamId ""` with `isTeamAdmin`/`isOwner` cleared. Last-admin guard: 409 if the person is the only active admin while others remain; the owner must transfer first (existing transfer flow); the sole remaining member may leave. Platform owner can force-remove. The profile stays. Entries, assignments and attendance stay with the team (uid-keyed; `scoutName` copies stay).
- **Past Team Members** (Assignments, collapsed by default): the section lists `memberships where teamId == X and status == past`, ordered by `leftAt`: name, role at the time, joined and left dates, events attended. Readable by active admins of that team only. A former member's name in old rows comes from the membership snapshot.
- **Events attended** today: `useTeamEventAttendance` (root `teams.eventAttendees`, FTC `eventAttendance`) then `lib/profile/stats.ts:83` counts events whose uid list contains the person. The attendance checklist is on the Assignments page (`MemberMultiSelect`, `assignments/page.tsx:259`), so the data is already "from Assignments". **Owner report (profile "Events" card):** 8 events shown (Arkansas 2 entries, Bayou 0, six others 0) when the team only attended Bayou and Arkansas in 2026, and the entry counts are wrong. Two code facts explain part of it: (1) `computeProfileStats` has NO season filter, while old CS counted only the current year (`CompSocrates (reference)/app/profile/[userId]/page.tsx:156`); (2) attendance keys are normalized (`attendanceRecordsFromTeam`, `normalizeEventKey`) but entries are counted under their raw `e.eventCode` (`stats.ts:82-85`), so an alias mismatch gives 0 entries even for Bayou. Not explained by code: why the person is listed in the attendance lists of six events the team did not attend (unverified: those lists may be stale CS data or events picked on the Assignments page). Archived events cannot be selected on Assignments, so a wrong list cannot be corrected in the UI. Fix (can be pulled forward as its own small session): filter by the program's season (`ProgramConfig` season rule), normalize both keys, count entries per event across `source` event/live only, add an "include archived events" selector to the Assignments attendance checklist so admins can correct it, and run a read-only audit of `teams.eventAttendees` for the affected person (keys vs entry `eventCode`) before changing any data. The membership model keeps uid, name snapshot and dates, and never prunes attendance uids. Assigned is not attended: attendance stays the source.
- **Rejoin:** restore the same membership doc (status active, `rejoinedAt`, keep original `joinedAt`, role set fresh by the approver) so history stays one record. Default role applies.

## 5. Account deletion (server job, Admin SDK)
Order: (1) refuse if the person is sole owner/admin of a team with members (same guards as leave); (2) write `accountDeletions/{uid}` (server-only; status, opaque id, per-step cursors); (3) disable the Auth user and revoke refresh tokens; (4) end every membership as `deleted`; (5) rewrite uid and name in the "rewrite" list in batches of 400 with the cursor stored after each batch, matching by `scoutId`/`uid` equality; (6) delete the "delete" list; (7) delete avatars and Blob files; (8) delete the Auth user; (9) delete the job doc. The opaque id is a random value with NO stored mapping, so one deleted person's rows stay grouped ("Deleted Account") but nothing links back. Idempotent: each step is a query that finds nothing once done. Resume: `CRON_SECRET` sweeper retries `running` jobs. Failure modes: partial rewrite leaves some names visible while the job runs (the person sees "deletion in progress"); rows matched only by name (old CS) are rewritten only when the name equals a membership name, else counted and reported; a crash between steps 3 and 8 leaves a disabled account, never a half-open one; re-sign-up with the same email is blocked until step 8. Blob hook: the later photo feature must store files under a uid-keyed prefix or an index doc (today paths are team-keyed, `blob-auth.ts:157`). Guard: a typed registry `PERSON_DATA_REGISTRY` (collection, fields, action) plus a test that fails when new code writes `scoutName`/`uid` to an unregistered collection.
- **Optional relink by verified email (default OFF).** Store `HMAC(secret, verifiedEmail)` in a tombstone beside the opaque id (new secret, name only: `RELINK_SECRET`). A new account with the same verified email may be offered relink only after adult-lead approval; relink rewrites opaque id to the new uid (name is NOT restored, since it was deleted). Trade-offs: the tombstone keeps a re-identifiable value (a small email space can be brute-forced if the secret leaks), it contradicts "everything else deleted", and the dialog must say so. **Recommend default off.** Not legal advice: FIRST teams include minors, so the owner should confirm retention and deletion with adult leads and the school/organization policy.

## 7. Rules and risk
- **New (additive, safe to deploy first):** `memberships` and `programs/ftc/memberships`: read when `uid == me`, or active member of the team (roster, via `sameTeam`), or `status == past` only for an active ADMIN of that team verified through their own membership doc (never the pointer); write false. Tamper risk low (read-only; a roster leak of names to teammates). `personalPractice` (root and FTC): self by path, no `teamId` key, write size bounded. `accountDeletions`: no client access (falls to the catch-all). Root `profiles` create must allow `teamId ""` for self (read self only; medium-low, test it). FTC `teams` update key allowlist gains `allowMemberRoleChoice` (admin-only boolean; low risk, the server still validates the role at approval).
- **Closing (after the app deploys, FTC only because it is rebuild-owned):** FTC `teams` create false; `users` owner-create and approval-create false; `joinRequests` approve client batch and self-create false (all move to routes). This closes client-side creation paths that bypass applications. Root rules stay as live CS needs them.
- **To server routes:** switch, leave, remove, role/admin edit (`updateMemberAccess`), FTC join approve/deny and create, application approval for FTC, share personal practice, account deletion, `request-join` (drop the "already has a team" 409; check duplicate membership).
- **Emulator tests:** a user cannot create or edit their own membership; cannot add themselves to a team (FTC: pointer locked; root: tested as far as the current rules allow); cannot escalate a role through a membership; a non-admin cannot read the past roster; a user who never belonged cannot read another team's past roster; after leave the FTC pointer is cleared and team reads are denied; personal sessions are unreadable to other users and to teammates; a personal session with `teamId` is refused; switch to a team without membership returns 403; last-admin guard; rejoin restores the doc.
- **Deploy order:** rules (additive) first, then the app, then the closing rules. Rules first is safe for live CS (no root CS rule changes; the already-pending non-FTC rule additions are covered in the local security notes). App before rules: new routes work (Admin SDK) but membership reads and personal practice are denied, so the switcher must fall back to "one implicit membership" on permission-denied. Closing rules before the app: FTC create/approve client batches fail (rebuild only).
