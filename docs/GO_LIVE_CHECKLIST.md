# Go-live checklist: CompSocrates v2 beta

Do it by hand, in order. **[OWNER]** = only the project owner can do it (console access, billing, account ownership). Nothing here is automated, and the release session never merged, deployed or touched a console.

Facts that shape the order:
- Previews and the live site share ONE Firebase project (Firestore and Auth) and, until a Production Blob store exists, one Blob store. A preview writes real data.
- The old app and v2 share Firestore, so every change is additive and the rules go first.
- `<project-id>` is the Firebase project id. `.firebaserc` only names a demo project, so ALWAYS pass `--project <project-id>`.
- Tag `live-before-v2` already marks the old live tip of `main` (98071e9) on origin.

## 0. Before anything else
1. **[OWNER] Confirm the GitHub repository is PRIVATE** before merging: GitHub > repository > Settings > General > Danger Zone > "Change visibility" (it must say Private); `docs/cs-firestore.rules` and the `CS-OPEN` comments in `firestore.rules` are tracked and describe open spots. Verify: open the repo URL in a signed-out private window and get a 404.
2. `docs/SECURITY-NOTES.md` is NOT tracked (ignored). Never `git add -f` it. Local branches `main-rebuild-archive` and `backup-before-filter` still hold it in history: never push them.

## 1. Back up and record the live state
3. **[OWNER] Back up Firestore.** Console > Firestore Database > Import/Export, or `gcloud firestore export gs://<bucket>/pre-v2-<date> --project <project-id>`. A managed export needs **billing enabled (Blaze plan) and a Cloud Storage bucket**. If the project cannot have billing, enable Blaze just for the export (cost is small; you can downgrade afterwards). There is no free full-database export. Last resort, not a backup: note the team count and a few sample documents, and rely on v2 being additive (it deletes nothing). Verify: the bucket folder exists and is not empty.
4. **[OWNER] Save the live rules text OUTSIDE the repo** (for example `../live-backup/rules-<date>.txt`): Console > Firestore Database > Rules > copy everything. Verify: the file opens and ends with the closing braces.
5. **[OWNER] Save the live index list OUTSIDE the repo:** `firebase firestore:indexes --project <project-id> > ../live-backup/indexes-<date>.json`. Answer NO to any prompt to delete indexes; never use `--force`. Verify: the file lists indexes (or `{"indexes": []}`).
6. **Compare the live rules with `docs/cs-firestore.rules`:** `diff <(tr -d '\r' < ../live-backup/rules-<date>.txt) <(tr -d '\r' < docs/cs-firestore.rules)`. Record the result in a note. Identical (comments aside): continue. Different: STOP and show the diff to the reviewer, because v2's rules were derived from the supplied copy, not from the live ones. Verify: the note exists.

## 2. Rules first (additive; the old app is unaffected)
7. **[OWNER] Deploy the FULL rules, rules only, at a quiet time** (rules take effect on live traffic immediately): `firebase deploy --only firestore:rules --project <project-id>`. Make sure you are signed in to the account that owns the project (`firebase login:list`). Do **NOT** deploy indexes: never run `firebase deploy` without `--only firestore:rules`, and do not use `firestore:indexes`. The live index list is unknown; if a query later reports a missing index, create it from the console link in that error. Verify: sign in on the OLD live site and open the dashboard and a scout form: it still works.
8. **Rules rollback** (keep it handy): paste the saved text from step 4 into Console > Firestore Database > Rules and Publish; or put it in a temporary `firestore.rules` in a scratch folder with its own `firebase.json` and run the same deploy command there. Verify: the console shows the earlier text and the old site still works.

## 3. Settings, keys and variables
9. **[OWNER] Create the settings document by hand** in the Firestore console: collection `appSettings`, document `global`, fields `teamCreationEnabled` = false (boolean) and `avatarUploadsEnabled` = false (boolean). Leave `adminsSeeAllProfiles` missing (missing means ON: team admins can read every teammate's profile; the owner decided to keep that) and do not create any membership field (that work does not exist yet). Verify: after the release, `/api/public/config` on the site shows `teamCreationEnabled: false` and `avatarUploadsEnabled: false`. A missing field already means off (the code defaults changed in this release), so this step is a belt-and-braces record.
10. **[OWNER] Service account (new key, then delete the exposed one).** First check Vercel > Project > Settings > Environment Variables whether Production already has `FIREBASE_ADMIN_CLIENT_EMAIL` and `FIREBASE_ADMIN_PRIVATE_KEY`. The old app may not use a service account at all (it has no firebase-admin code), so the exposed key may only matter as an exposed credential; v2 REQUIRES the pair for every server route. Then: Google Cloud Console > IAM & Admin > Service Accounts > the Firebase Admin SDK account > Keys > Add key > Create new key > JSON. Put `client_email` and `private_key` into `FIREBASE_ADMIN_CLIENT_EMAIL` / `FIREBASE_ADMIN_PRIVATE_KEY` for **Production AND Preview** (the key on one line with `\n` escapes, no quotes). Redeploy. Verify: sign in, open event data (no 503 `server_not_configured`). ONLY THEN delete the exposed key in the same Keys list, and delete the downloaded JSON from your disk and the Recycle Bin. Verify: the Keys list no longer shows the old key id and sign-in still works. After that, review the account's audit log for unexpected use of the old key.
11. **[OWNER] Set the Production variables** in Vercel (names only; Preview too where you will test). Required: `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`, `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID` (same as today); `NEXT_PUBLIC_TBA_API_KEY` (a server secret despite the name; event data), `FIRST_API_USERNAME` and `FIRST_API_TOKEN`; `RELEASE_OWNER_UIDS` and/or `RELEASE_OWNER_EMAILS`; `FIREBASE_ADMIN_CLIENT_EMAIL` and `FIREBASE_ADMIN_PRIVATE_KEY`. By feature (optional, off when unset): FTC event data `FTC_API_USERNAME`, `FTC_API_KEY` (`FTC_API_BASE_URL` optional); live-score poller `CRON_SECRET` (the new daily cron answers 503 without it); email `RESEND_API_KEY` + `EMAIL_FROM` and links `APP_URL`; application bot check `NEXT_PUBLIC_TURNSTILE_SITE_KEY` + `TURNSTILE_SECRET_KEY` (both or neither); push `NEXT_PUBLIC_FIREBASE_VAPID_KEY`; `APPLICATION_SECRET`; `NEXT_PUBLIC_RELEASE_OWNER_UIDS`; photos and avatars `BLOB_PUBLIC_READ_WRITE_TOKEN`. The old app's `MIGRATION_EMAIL`, `MIGRATION_PASSWORD`, `TBA_KEY_ENCRYPTION_SECRET` and `USER_DATA_ENCRYPTION_SECRET` are not read by v2: remove them after the release. Details and consequences: `docs/ENVIRONMENT.md`. Verify: Admin Panel > Setup Check (step 17) lists nothing you meant to set.
12. **[OWNER] Create a SEPARATE Production Blob store** (Vercel > Project > Storage > Create > Blob, access **Public**; it cannot be changed later) and connect it to **Production only** with the prefix `BLOB_PUBLIC`, so Production gets its own `BLOB_PUBLIC_READ_WRITE_TOKEN`. Keep Preview on a different store (or none), so a preview cannot modify production files. Avatars stay off (`avatarUploadsEnabled` false) but form photos use this store. Verify: Vercel shows different tokens for Production and Preview.
13. **[OWNER] Confirm Preview variables** are set (the same list, with the Preview Blob token) and **Firebase Authentication**: Console > Authentication > Sign-in method has Email/Password and Google enabled; Settings > Authorized domains lists compsocrates.com and the specific preview domain you will test on (no wildcards). Verify: Google sign-in works on both.

## 4. Test a preview against real data, then release
14. Push `release-prep` (done by the release session) and open the Vercel PREVIEW deployment for it. **It writes real production data.** Run `docs/SMOKE_TEST.md` on the preview with a test event and a test team. Verify: all ten steps pass and the browser console shows no permission-denied.
15. **[OWNER] Release.** Open the PR "CompSocrates v2 (beta)" (release-prep into main) and merge it with a **merge commit**: NOT squash and NOT rebase, or the history link built for this release is lost. Before merging, check once more that `git ls-remote --tags origin live-before-v2` still shows 98071e9. Watch the Vercel build for the production deployment. Verify: the deployment is Ready and compsocrates.com loads.
16. **[OWNER] Confirm the flags** in the console: `appSettings/global.teamCreationEnabled` is false and `avatarUploadsEnabled` is false (or missing). Do not set either true during the beta.
17. **[OWNER] Sign out and sign in as the platform owner** so the owner claim refreshes (the sign-in sync sets it from `RELEASE_OWNER_UIDS` or a verified email in `RELEASE_OWNER_EMAILS`). Open Admin Panel > Setup Check and clear what it lists. Verify: the Admin Panel shows the owner-only tabs and Setup Check is clean.
18. Run `docs/SMOKE_TEST.md` on compsocrates.com. Verify: all ten steps pass.

## 5. Cleanup after the old app is gone
19. **[OWNER] Rotate keys the old app exposed to browsers:** the TBA key and the FIRST token (the old app shipped both to every visitor). Create new ones at The Blue Alliance (Account > Read API keys) and FIRST, update `NEXT_PUBLIC_TBA_API_KEY`, `FIRST_API_USERNAME`, `FIRST_API_TOKEN` in Vercel, redeploy. Verify: event names still resolve.
20. **[OWNER]** Delete `ce-users.json` (outside the repo, in `compsocrates-rebuild/`) once migrated users have signed in, empty the Recycle Bin and look for copies; then retire the old sister project's service-account key and its Auth users when they are no longer needed. Details: `docs/SECURITY-NOTES.md` section 5 (local file).
21. **[OWNER] Changelog.** Edit the v2.0.0 template in Admin Panel > Changelog: its "several teams per account" line describes FTC field teams and must be reworded or dropped (v2 still has one team per account). Publish it as a BETA entry titled "CompSocrates v2.0.0 (beta)". Verify: it appears first, above the Legacy entries.

## 6. Rollback plan
22. **First, Vercel:** Project > Deployments > the previous Production deployment > "Promote to Production" (instant; no git needed). Verify: compsocrates.com is the old app again and sign-in works.
23. **Then fix `main`** so the next push does not redeploy v2: on a clone, `git checkout main && git revert -m 1 <merge commit> && git push origin main` (a normal revert commit; never force-push). The merge commit is the PR's merge commit (GitHub's "Create a merge commit" button always makes one, even though release-prep already contains main's history); `-m 1` keeps the old line. To release v2 again later, revert that revert first.
24. **Rules:** v2's rules are additive; the old app works with them, so leave them unless you must undo: restore the saved text (step 8). **Data:** nothing is deleted on rollback. The additive fields on existing documents and everything under `programs/ftc` stay in place; the old app ignores them. **Confirm:** the old site loads, an existing account signs in, a scout form submits, and the Vercel dashboard shows the old deployment as Production.

## 7. After release
25. Watch Vercel logs (Project > Logs: 401/403/500 on `/api/*`) and Firestore usage (Console > Firestore > Usage: reads and writes against the free quota) for a day. The first `/api/public/config` reads are now side-effect free.
26. **Post-release hardening, in this order** (each needs its own session, rules tests and a re-deploy by hand):
    1. Tighten root team creation (the root `teams` create is open to any signed-in user) and the `users` self-write of `teamId`, `role` and `isTeamAdmin` (inherited CS rules; the old app may need them until it is retired). Until then, FRC team creation is closed in the app and the server route only; the rules still allow it.
    2. The collection-group `list` residual on `scouts` and `players` (a team-code clash between programs; `docs/SECURITY-NOTES.md` 3a).
    3. The hardcoded owner uid in the rules: move owner checks to the `platformOwner` claim.
    4. `npm audit` follow-ups: `docs/SESSION_I_RESULTS.md` lists each critical and high finding, with what a non-breaking fix needs.
27. Build the membership work (`docs/MEMBERSHIP_PLAN.md`) as a branch from `main` after the release; hand-clean the legacy changelog entries; run Playwright on every spec and Lighthouse; open the pages that have never been opened in a browser; deal with the left-behind branches (`CompSocrates-v2`, `preview`) listed in `docs/SESSION_I_RESULTS.md`.
