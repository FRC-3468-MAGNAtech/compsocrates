# Batch 7 plan: FTC event page, Performance Reliability, Robot Radar
Phase 1 only (no code changed). Findings are from reading the code, nothing was run.

## 0. Headline findings
- **None of the three pages uses EPA, Statbotics or TBA today.** The event page (`event-details-view.tsx` and its Overview/Teams/Schedule/Rankings tabs) reads `getEvent`, `getTeamsForEvent`, `getMatchesForEvent`, `getRankingsForEvent` only. So there is nothing to hide behind a capability flag. `event.hasEpa` already exists in `ProgramConfig` (FRC true, FTC false) and is unused; I would leave it unused.
- **The FTC provider already has everything the event page needs** (`lib/ftc/provider.ts`: event, teams, rankings, qual and playoff matches, bracket) and `lib/events/actions.ts` already takes a trailing `program`.
- **Existing bug that blocks parity:** the Teams, Schedule and Rankings tabs call the actions WITHOUT `program` (so FTC would read the FRC provider) and their cache keys are not program-scoped. Only the top-level `getEvent` passes `program`.
- **Robot Radar is REBUILT end to end** (axes, Hub IQ, tower weights, `CURRENT_GAME_ID` text, climb box plot, FRC lead-scout skill keys). It cannot show BIOBUZZ data without a per-game profile. This is the real design question (D2).

## 2. FTC event page: route and key
Today the route takes a TBA key (`2026lake`); season = 4-digit prefix. FTC needs season plus code (FTC codes repeat each season).
- **Proposed FTC key: `{season}-{CODE}`, e.g. `/ftc/events/2025-USCALAB`.** URL safe, program-agnostic route, cannot match the FRC regex `^\d{4}[a-z0-9]+$` (the hyphen), so `isTbaEventKey`, `lookupSeasonForKey` and the FRC name store ignore it. Build uppercases the code; parse accepts any case.
- ONE pure module `lib/events/event-key.ts`: `parseEventKey(shape, key) -> {season, code} | null`, `buildEventKey(shape, season, code)`. `ProgramConfig.event.keyShape: "tba" | "season-code"` (additive config; FRC "tba" = today's behaviour exactly). No program-id comparisons.
- Everywhere a key is parsed, built, linked or compared: BUILD `selected-events-panel.tsx:412` (the only link; needs `event.season`); PARSE `event-details-view.tsx` + `details-model.eventKeyYear` (both replaced by `parseEventKey`); `config/event.ts` `getSeasonFromEventKey/isTbaEventKey/normalizeEventKey` (lowercases; not used for FTC keys); `name-store.lookupSeasonForKey` (returns null for FTC: no FRC request, correct); page `decodeURIComponent` (unchanged); legacy `/event-details/:eventKey` redirect (FRC only, untouched). Page title uses the resolved name; no breadcrumbs or exports reference this key; `lib/seasons` is game seasons, not keys; `lib/active-event` stores bare codes and is untouched. An FRC key under `/ftc/...` (and the reverse) shows the NotFound card.
- FTC Events API gives: event details, dates, location, venue, website, timezone, team list, qual and playoff schedule with results, rankings. The client fetches all of them already; no new endpoint.

## 3. Event status (Session D)
The page uses `eventBadge` -> `getEventStatus` (whole calendar days in the event's timezone, computed fresh at render, not the frozen `EventInfo.status`), so a finished event reads "Completed", never live. Archived events are hidden only from pickers, a direct URL still works. Same code for FTC; add tests for unstarted, running, finished. Not-started events show empty tabs with the existing empty texts.

## 4. Rules and data paths
No rules change. The event page reads only session-gated server actions (FTC API, `FTC_API_USERNAME`/`FTC_API_KEY`); no Firestore read. The two analytics pages read through the existing ports (`programs/ftc/scoutEntries`, `formEntries`, `practiceSessions`, team-wide `teamId ==`), which the FTC rules already allow. No root collection, no collection group, no new index.

## 5. Design
- **Event page:** keep `EventDetailsView` and the four tabs. Changes: pass `program` into Teams, Schedule, Rankings (and use `scopedKey`) so results are cached once per event per program and shared by the tabs; `parseEventKey`; config-driven labels (`event.codeLabel` "Event Key"/"Event Code", credits text and link, season shown as 2025-26 for `start-year`). Missing or rejected key: the existing error card shows the typed message (names the variable), the header still shows the stored name from the chain. Link builder takes the season.
- **Performance Reliability:** no component change expected beyond D3. Config only.
- **Robot Radar (if D2 = B):** add an optional `radar` profile to the game definition. REBUILT's profile reproduces today's five axes and box plot (golden test, FRC numbers identical). BIOBUZZ profile (proposal): Auto, Teleop, Endgame (each mean points relative to the best team), Reliability (from the existing `reliability` stat roles: share of matches with no incident). Hive and Garden points use recorded-only means and carry the alliance label. No Agility axis and no box plot for BIOBUZZ (no FTC lead-scout skill source and no climb): hidden, not greyed. Axis count is data driven; the chart must accept 4 or 5 axes.
- **Config:** `ftc.ts`: remove the three paths from `FTC_UNAVAILABLE_PATHS`, add them to `connection.paths` (`/events/[eventKey]`, both analytics paths); `types.ts`: `keyShape`, `codeLabel`, `eventDataCredit`; `frc.ts`: matching values. Sidebar, tab strip and customizer need no code (the resolver reads `unavailablePaths`).
- **Tests:** per page with 2-team and 3-team data (event page via mocked fetch), absent role values, few/no entries, unstarted/running/finished, key build/parse round trip and FRC non-collision, missing and rejected keys, FRC reads exactly the same calls (assert args), resolver lists the three pages for both programs, no root collection for FTC, radar golden test for REBUILT. `config/parity-guard.test.ts`: no new `useProgramData()` reader planned.
