**Done (nothing run in a browser: no keys here).** `/team-settings` and `/changelog` are connected for FTC; the `changelog` flag is on. **Rules: unchanged, nothing to deploy.**
**Task 0 findings that changed the plan.** (1) CE's `/api/team/sync-field-teams` is NOT an admin edit route: it takes no input, never calls the FTC API, any member may call it, and it is an idempotent repair of `fieldTeams` and members' `fieldTeamIds`. **Team Settings.** `AccountTeamsSection` (shared rules in `lib/account-teams.ts`): add, rename (name and number), remove, with a dialog; an audit entry for each change, in the same batch (`saveAccountTeams` through the port: team doc, then members' `fieldTeamIds`, then the log). Add and rename save from a dialog; only removal asks "are you sure". Removing is **refused** while any non-admin member is assigned to the team (names shown) and for the last team. **Entries never store an account team, so nothing can be orphaned.** Member assignment: tick teams per member (at least one stays; a member with none ticked counts as all). A member sees only assigned teams in the switcher; **an admin now sees all** (`lib/our-team.ts`, FTC only in effect). The assignment batch carries the unchanged team list, because the rules check an assignment against the team doc's own id list, which an account that predates the list lacks (emulator-tested). Name lookup: server only (`ProgramData.team.lookupTeamName`); a missing or rejected key shows the typed names (`FTC_API_USERNAME`, `FTC_API_KEY`), manual entry still works. Non-admins see the list read-only (as FRC's page does for the name and number). Loading, empty, saving and error states are all there; a failed team read says so.
